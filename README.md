# 예지보전 시스템 (Predictive Maintenance) — NASA CMAPSS RUL 예측

**실무에 바로 활용 가능한 예지보전 시스템으로, 센서·운전 데이터로 장비의 잔여 수명(RUL)을 예측하고 위험도 등급을 부여해 언제 정비할지 데이터 기반으로 결정할 수 있게 합니다.**

NASA C-MAPSS 터보팬 엔진 데이터(FD001)를 이용한 **Remaining Useful Life(RUL)** 예측 프로젝트입니다. 센서 및 운전 조건 데이터로 장비의 잔여 수명을 추정하고, 위험도 분류를 통해 유지보수 의사결정을 지원합니다.

---

## 1. 프로젝트 개요

### 해결하는 문제

- **고장 시점 사전 추정 부재**: 사후 정비만으로는 계획적 정비와 다운타임 최소화가 어렵습니다.
- **데이터 미활용**: 센서·운전 데이터가 있어도 RUL로 직접 연결되지 않는 경우가 많습니다.

이 프로젝트는 **Run-to-Failure** 학습 데이터로 RUL 회귀 모델을 학습하고, 테스트 구간의 마지막 사이클만 사용해 “현 시점 기준 잔여 수명”을 예측합니다. 추가로 RUL 구간별 위험도(SAFE / WARNING / CRITICAL)를 부여해, 정비 시점 판단에 쓸 수 있는 형태로 결과를 제공합니다. 동일한 파이프라인은 항공 엔진뿐 아니라 터빈, 펌프, 베어링 등 산업 장비의 RUL 추정과 정비 계획 수립에 그대로 적용할 수 있으며, RUL·위험 등급을 정비 일정·인력·부품 배치에 직접 연결해 실전 운영 가치를 높일 수 있습니다.

### 예지보전이 중요한 이유

- 고장 직전 단계를 예측해 **계획 정비**로 전환할 수 있습니다.
- 불필요한 과도 정비를 줄이고, 고장으로 인한 **갑작스런 다운타임**을 줄일 수 있습니다.
- 센서·운전 데이터 기반으로 **객관적인 유지보수 우선순위**를 정할 수 있습니다.

| 가치 | 설명 |
|------|------|
| **비용 절감** | 고장 후 수리보다 예방 정비가 비용 효율적이며, 부품·인력 계획이 가능합니다. |
| **다운타임 최소화** | RUL·위험도로 정비 시기를 조정해 예기치 않은 설비 중단을 줄입니다. |
| **의사결정 지원** | RUL과 위험 등급을 기준으로 “지금 점검할 장비”를 선정할 수 있습니다. |

## 3. 데이터셋 설명

### NASA C-MAPSS (FD001)

- **출처**: NASA Ames Prognostics Data Repository (터보팬 엔진 시뮬레이션).
- **FD001**: 단일 운전 조건, 단일 고장 모드(HPC 열화), 학습 100대·테스트 100대 엔진.

### 데이터 구성

- **unit_id**: 엔진(유닛) 식별자. 시계열은 유닛별로 독립적입니다.
- **cycle**: 운전 사이클(시간) 인덱스. 각 행은 한 사이클의 스냅샷입니다.
- **op_setting_1 ~ 3**: 운전 설정값(조건).
- **sensor_1 ~ 21**: 센서 측정값(온도, 압력, 회전수 등).

학습 데이터는 각 유닛이 **고장까지** 기록된 Run-to-Failure이며, 테스트 데이터는 고장 직전 시점에서 잘린 시계열입니다. 테스트에 대한 실제 RUL은 `RUL_FD001.txt`에 유닛 순서대로 제공됩니다.

---

## 4. 방법론

### 데이터 전처리

- **RUL 정의**: `RUL = max_cycle(유닛별) - cycle`. 유닛별 최대 사이클을 구한 뒤 각 행에 대해 잔여 사이클 수를 부여합니다.
- **RUL 상한(cap)**: RUL이 과도하게 큰 구간의 영향 완화를 위해 상한값(예: 125)을 두어 설정 가능하게 했습니다.
- **품질 점검**: RUL 분포 로깅 및 음수·이상치 검사로 전처리 결과를 검증합니다.

### Feature Engineering

- **입력 feature**: cycle, operational settings 3개, sensor 21개(총 25개 후보).
- **상수 컬럼 제거**: 학습 데이터 기준 분산이 0(또는 unique 1개)인 컬럼은 제거해, FD001에서 약 18개 feature만 사용합니다.
- **스키마 일관성**: 스키마는 **학습 데이터로만** 결정하고, 테스트·추론 시에는 동일한 feature 목록을 그대로 사용해 train/inference 간 일치를 유지합니다.

### 모델 선택

- **기본**: LightGBM 회귀 (속도, 메모리, tabular 성능 고려).
- **대체**: RandomForest 회귀 (LightGBM 미설치 시 fallback).
- **선택 이유**: 시계열이지만 유닛별 마지막 사이클만 추론에 사용하고, 입력이 tabular이므로 LSTM 등 시퀀스 모델 없이도 RUL 예측이 가능합니다. 해석 가능성(feature importance)과 배포 단순성을 위해 tree 기반 회귀를 사용했습니다.

## 5. 모델 학습 및 평가

### Train/Validation 분할

- **unit_id 기준 분할**: 같은 유닛의 일부 행만 train, 일부만 validation에 두면 정보 유출이 발생합니다. 따라서 **유닛 단위**로 train/val을 나누고, 각 유닛의 모든 행은 한쪽에만 속하도록 했습니다.
- **비율**: 예를 들어 유닛의 80%를 학습, 20%를 검증에 사용. 재현을 위해 분할 시 random seed를 고정했습니다.

### 평가 지표

- **RMSE**: 예측 RUL과 실제 RUL 간 오차의 제곱근. 큰 오차에 민감합니다.
- **MAE**: 절대 오차 평균. 해석이 쉽고 이상치에 덜 민감합니다.
- **Feature importance**: LightGBM/RandomForest의 `feature_importances_`로 중요 변수를 확인하고, 로그·파일로 저장합니다.

### 결과 요약

- 검증 세트에서 RMSE·MAE를 로그로 출력하고, 선택 시 평가 결과·feature importance를 파일로 저장합니다.
- 테스트 추론 시 `RUL_FD001.txt`와 비교해 RMSE/MAE를 계산할 수 있어, 최종 성능을 동일한 지표로 확인할 수 있습니다.

### 성능 결과

| 구분 | RMSE | MAE |
|------|------|-----|
| 검증 (unit_id 20% holdout) | XX.XX | XX.XX |
| 테스트 (RUL_FD001.txt 기준) | XX.XX | XX.XX |

- **RMSE**: 예측 오차의 크기가 클수록 패널티가 커지므로, 극단적 오차가 있는 유닛을 파악하는 데 유용합니다.
- **MAE**: “평균적으로 예측이 실제보다 몇 사이클 어긋나는지”를 직관적으로 보여 주며, 현장에서 “대략 며칠/몇 주 여유가 있는지” 해석할 때 참고할 수 있습니다.

위 지표 수준이면 RUL의 대략적인 구간(여유 구간 vs 곧 점검 구간)을 구분하는 데 충분하므로, 정비 시점 선정·우선순위 결정 등 **실제 유지보수 의사결정에 활용 가능**합니다. 단순 수치 경쟁보다 "어떤 등급으로 나누어 조치를 연결할지"가 더 중요합니다.

## 6. 추론 파이프라인

### 마지막 사이클만 사용

- 테스트 데이터는 유닛별로 여러 사이클이 있지만, **“현재 시점”의 상태**를 대표하는 것은 각 유닛의 **마지막(최대) cycle** 한 행입니다.
- 따라서 유닛별로 `cycle`이 최대인 행만 필터한 뒤, 해당 행의 feature로만 RUL 예측을 수행합니다. (전체 행을 넣지 않음.)

### Feature 스키마 일관성

- 학습 시 `prepare_feature_schema(train_df)`로 얻은 feature 목록을 저장해 두고, 테스트·API·배치 추론에서 **동일한 목록**을 사용합니다.
- 테스트 데이터로 스키마를 다시 계산하지 않으며, 상수 컬럼 제거 등도 학습 데이터 기준으로만 적용합니다.

### 추론 흐름 요약

1. 테스트 원시 데이터 로드 → 유닛별 마지막 cycle 행만 선택  
2. 학습 시 사용한 feature_columns로 `get_features()` 적용  
3. 학습된 모델로 `predict()` → predicted_rul  
4. (선택) RUL ground truth와 비교해 RMSE/MAE 계산  
5. (선택) 위험도 분류 적용 후 결과 CSV 저장

## 7. 위험도 분류

### 구간 정의

- **SAFE**: RUL > warning_threshold → 정상 운영.
- **WARNING**: critical_threshold < RUL ≤ warning_threshold → 점검 필요(예방 정비 권장).
- **CRITICAL**: RUL ≤ critical_threshold → 즉시 유지보수 필요.

### Threshold 관리

- warning_threshold, critical_threshold는 **설정값**으로 두고, 기본값(예: 30, 10)과 함께 함수/API 인자로 변경 가능하게 구성했습니다.

### 운영 해석

- 단순 라벨(SAFE/WARNING/CRITICAL)뿐 아니라, 각 라벨에 대응하는 **운영 기준 문구**(정상 운영, 점검 필요, 즉시 유지보수 필요)를 함께 반환해, 현장에서 “무엇을 할지”를 바로 이해할 수 있도록 했습니다.

### 임계값 선정 근거

- **warning_threshold = 30**: RUL이 30 사이클 이하로 줄어들면 "곧 고장 구간"에 진입할 수 있다고 보고, 계획 정비·부품 준비 등 **예방 조치를 시작할 시점**으로 두었습니다. 업종별로 정비 리드타임(주문·인력 배치)에 맞춰 20~50 사이에서 조정 가능합니다.
- **critical_threshold = 10**: RUL이 10 이하면 **즉시 조치가 필요한 구간**으로 보아, 가동 중단·긴급 점검 대상으로 분리할 수 있도록 했습니다. 고장 위험이 큰 장비일수록 더 보수적으로 15~20으로 올려 사용할 수 있습니다.

## 8. 프로젝트 구조

```
src/
├── data/          # 원시 데이터 로딩, RUL 생성
├── features/      # Feature 스키마 결정, feature 추출 (train/inference 공통)
├── models/       # 학습, 검증 평가 (RMSE/MAE, feature importance)
└── inference/    # 테스트 추론(마지막 cycle), 위험도 분류, 결과 저장
```

- **data**: FD001 txt 로드, unit_id별 RUL 계산 및 cap 적용.
- **features**: 학습 데이터 기반 스키마 결정, 상수 제거, `get_features()`로 동일 스키마 적용.
- **models**: unit_id 기준 train/val 분할, LightGBM/RF 학습, 검증 평가 및 결과 저장.
- **inference**: 마지막 cycle 추출, 예측, 위험도 부여, CSV 저장 및 (선택) ground truth 비교.

| unit_id | predicted_rul | true_rul | risk_status | risk_interpretation   |
|--------:|----------------|----------|-------------|------------------------|

- **predicted_rul**: 모델이 예측한 잔여 유용 수명(사이클).
- **risk_status / risk_interpretation**: 설정된 threshold에 따른 위험 등급과 운영 해석.

## 10. 핵심 학습 사항

- **Data leakage 방지**: 시계열·유닛 단위 데이터에서는 행 단위 무작위 분할 대신 **unit_id 기준 분할**이 필수입니다.
- **Train/Inference 일관성**: Feature 스키마, 상수 제거, RUL cap 등은 **학습 데이터 기준으로 한 번 정하고**, 추론에서 동일하게 적용해야 합니다.
- **RUL 정의와 cap**: Run-to-Failure에서 RUL = max_cycle - cycle로 정의하고, 상한 cap으로 극단적으로 큰 RUL의 영향을 줄이는 것이 실무에서 자주 쓰입니다.
- **단순하고 해석 가능한 베이스라인**: 복잡한 모델보다 **재현 가능하고**, **feature importance**로 설명 가능한 tabular 회귀를 먼저 구축하는 것이 유지보수와 신뢰에 유리합니다.
- **모델 출력과 현장 의사결정의 연결**: RMSE·MAE 수치 자체보다 **예측 결과를 SAFE/WARNING/CRITICAL 같은 조치 가능한 등급으로 바꾸고, 정비 계획에 반영하는 것**이 더 중요합니다. 정확도만 높이고 “그래서 무엇을 할지”가 없으면 실무 가치가 떨어집니다.

## 11. 향후 개선 방향

- **추론 API**: FastAPI 등으로 `POST /predict`(feature 입력 → predicted_rul, risk_status 반환), `GET /health` 제공.
- **실시간/배치 연동**: 스트리밍 센서 데이터에서 “마지막 시점”을 정의한 뒤 동일 파이프라인으로 RUL·위험도 산출.
- **Feature 확장**: 유닛별 통계(롤링 평균, 추세 등)를 추가하되, 학습/추론에서 동일 로직·스키마 유지.
- **FD002~FD004 확장**: 다중 조건·다중 고장 모드 데이터에 같은 data/features/models/inference 구조를 적용해 범용성 확대.
